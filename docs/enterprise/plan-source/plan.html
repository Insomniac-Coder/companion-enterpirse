Initial draft for discussion

Companion Enterprise

Architecture and action plan
6 October 2026 Working title Built on the Local LLM PC Companion

We will turn the Local LLM PC Companion, today a one-person app on one PC, into a shared company service. People use a desktop app, signed in with their company account. A server, which can run on one machine or across many, hosts our own open-weight models and can also pass requests to OpenAI, Anthropic or Google. It answers from company documents with citations (RAG), connects to Jira and Outlook, gives each team only the tools it is allowed, and records who asked what in an audit log. A separate dashboard lets the team running it manage models, users, tools, rules and costs.

For people using it

  • Install an app, sign in with the company account
  • Pick from the models the company approved
  • Get answers from company documents, with the sources named (RAG)
  • Switch on the plugins their team is allowed
  • Connect their own Jira and Outlook
  • The coding agent works on files on their own PC

For the team running it

  • One dashboard: models, providers, users and groups, tools, documents, rules, audit log, usage
  • Settings set and locked centrally
  • Add a model or a provider without touching the apps

For the company

  • With our own models, nothing leaves the building
  • Outside providers only through our rules
  • A complete, tamper-evident audit trail
  • Costs visible per person and team
  • Grows by adding servers

02Where we start

The Companion is one program on one PC: a Rust backend that does the work, React screens in the browser, a llama.cpp model server it starts and tunes itself, and one database file. About 34,000 lines of backend code (48,000 with tests), 12,000 lines of screens, and more than 600 automated tests.

What we keep

  • The coding agent: reads, writes, runs and checks project files, and stops itself when it is stuck in a loop
  • Permission modes: ask, accept edits, plan, auto
  • The test that checks whether a model can really call tools and write files intact
  • Memory management for long tasks
  • llama.cpp tuning: memory fit and per-model calibration
  • Full logs on disk, saved as a zip to share

What has to change

  • Nothing knows who is asking: there is one user
  • One loaded model at a time
  • One database file on one PC
  • One settings file shared by everything
  • The agent's tools assume the files are on the same machine as the server
  • It only accepts connections from the same PC

Simplified on purpose. One company per installation (serving several companies from one installation is not planned). One backend program with two roles instead of many small services. Background jobs are queued in PostgreSQL itself, with no separate queue product until measurements say otherwise.

04How a request travels

A chat message

  1. The app sends the message with the person's sign-in token. The server knows who they are, their groups and their settings.
  2. Checks: is this model allowed for them, and is there budget left?
  3. If document search is on, it finds passages, only from documents this person may open.
  4. It builds the request with the conversation's start kept unchanged, so the model does not re-read it (the Companion's speed trick).
  5. If the model is outside the company, the request is scanned for secrets and personal data, and collections marked "never send outside" are left out.
  6. The same conversation always goes to the same copy of a local model, so that copy reuses what it already read.
  7. The reply streams back; if the person is connected to another server, Redis carries it across.
  8. An audit record and the usage count are written.

A coding-agent task

  1. The user starts a task in the desktop app on a folder of their PC.
  2. A worker takes the task and runs the Companion's agent loop: ask the model, carry out its next step, repeat.
  3. Steps that touch the PC (read or write a file, run a command, preview a page) go to the app over the device channel. The app checks the folder is allowed, asks the user when the mode requires it, does the work and returns the result.
  4. Steps that live on the server (document search, Jira, Outlook, web search) run in the worker.
  5. The host's own looks at the project (project summary, instructions file, git status, notes) also go through the app.
  6. If the app disconnects, the task pauses and waits instead of failing.
  7. Every step is recorded on the server.

06Models: our own and outside providers

  • One model list. Each entry is either a local model or a provider's model, with: engine, the smallest and largest number of copies, which groups may use it, and its abilities.
  • Two engines for our own models. llama.cpp runs anywhere, including laptops and machines without a GPU, and keeps the Companion's tuning. vLLM serves many people at once from large GPU servers (Linux).
  • Outside providers through two small adapters. One speaks the OpenAI format, which covers OpenAI, Azure OpenAI, vLLM, llama.cpp and Google Gemini's compatible endpoint; one speaks Anthropic's own format, which handles tools better for Claude.
  • Linking a provider takes four steps in the dashboard: add it (type, address, key), test the connection, pick which of its models to offer, and give them company names. A name such as "company-default" can point at any model and be moved later without touching the apps.
  • Abilities are measured, not assumed. Today the Companion tests each model once: can it call a tool, and can it write a file intact? Every model gets this test, outside ones included, and the result is recorded with its context size, vision and reasoning.
  • Limits. Tokens and money per person, team and model; usage shown in the dashboard.

07Tools, plugins and MCP

MCP is an open standard for connecting AI apps to tools. An MCP server is a small program or web address that offers a set of tools, such as "search Jira issues" or "draft an email". Many services now publish one.

  • One plugin format. A plugin is an MCP server plus a short description: its name, each tool's risk (reads, writes, or dangerous), what it needs from the model, and which account it needs. The Companion's own file and command tools are described the same way.
  • Three levels of control. The admin's catalogue decides which groups get each plugin, which actions always need approval, and whether it may be used with outside models. Users switch on what they are allowed. Each request offers the model only tools that are switched on, allowed, and usable by that model.
  • Can this model use it? Each plugin states what it needs (tool calling, writing, a minimum context, vision). A plugin the chosen model cannot use is greyed out with the reason, and the server refuses it anyway. Models with no tool support get chat and reading only.
  • Adding one. Remote MCP servers are added by address. MCP servers that run as programs are installed by admins only.

08Jira and Outlook

ServiceHow we connect
Jira CloudAtlassian's official MCP server (generally available since February 2026). It respects each person's own Jira permissions.
OutlookOur own small MCP server over Microsoft Graph, Microsoft's standard interface to mail and calendar. Microsoft's official mail server is a preview that needs a Microsoft 365 Copilot licence. Read, search and draft first; sending only after the user approves.
Gmail (later)Google's official Gmail MCP server is a developer preview that reads and drafts but cannot send; reviewed when Gmail is scheduled.

Each person connects their own account through the usual "Sign in with Microsoft / Atlassian" screen, so the model can only see and do what that person can; their sign-in tokens are stored encrypted on the server. Sending an email or changing a ticket always asks first, whatever mode the user is in, because an email is the easiest way to slip instructions to a model; text from emails is treated as information, never as orders.

09Document search (RAG)

RAG hands the model the right passages from company documents at the moment a question is asked, so it answers from them and cites them. Today the Companion searches one project's files by keyword.

  • Collections: company-wide, team and personal, each with group access.
  • Reading in: upload or connect a source; a worker pulls the text out, splits it into passages and gives each a "meaning fingerprint" (an embedding) using a local model.
  • Searching: by meaning and keywords together, best matches first, with citations in the answer.
  • Access rights at search time: a person only gets passages from documents they may open.
  • Labels: a collection marked "never send outside" is only used with our own models; an "answer only from sources, or say you don't know" mode per assistant.
  • Sources: uploads and shared folders first; Jira and other company systems later, through the same connectors as the tools.

12Installing and scaling

One machine (laptop or one server)

  • One start script, including on a Windows laptop
  • The server, PostgreSQL, and llama.cpp model processes, as the Companion runs them today
  • No Redis; files in a folder
  • Used for the pilot and for running models locally

Many servers (our own or AWS)

  • Packaged as containers: sealed bundles that run the same on any server
  • Run by Kubernetes, which starts copies across servers, replaces failed ones and adds or removes copies
  • One install package (a Helm chart) for both our own servers and AWS
What scalesSignalNotes
API serversRequests and CPU loadCheap to add; hold no state
WorkersJobs waiting in the queueAgent runs and document reading
Model poolsRequests waiting for that model (both engines report it)Not CPU: a GPU server is full long before its CPU is busy
Limits worth knowing. On our own servers, scaling can only share out the GPUs we own between models; in AWS it can add GPU machines. A model can be set to switch off when idle, but the next request then waits for it to load, which can take minutes for a large model.

17Terms used

Audit log
A record of who asked what, which documents and tools were used, and what was decided.
Container
A sealed bundle of a program and everything it needs, which runs the same on any server.
Embedding
A list of numbers that captures what a passage means, so passages can be found by meaning.
Kubernetes
The standard system for running containers across many servers; it restarts failed copies and adds or removes copies.
llama.cpp
A model server that runs open-weight models on almost any machine; the Companion uses it today.
Load balancer
The front door that spreads incoming requests across the server copies.
MCP
Model Context Protocol: an open standard for connecting AI apps to tools.
OpenAI format
The request format most AI tools speak; offering it lets existing tools use our models.
pgvector
An add-on that lets PostgreSQL search by meaning.
RAG
Retrieval-augmented generation: giving the model relevant passages from our documents when a question is asked.
Redis
Fast shared memory used so several servers can pass live replies and counters to each other.
Tauri
A way to package web screens as an installable desktop app with a small Rust core.
vLLM
A model server built to serve many people at once from large GPUs.
